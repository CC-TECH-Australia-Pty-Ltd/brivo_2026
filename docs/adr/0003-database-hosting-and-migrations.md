# ADR 0003: Database hosting, schemas and migrations

**Status:** Proposed · 2026-11-03 · Source: *Brave Clinical System - Stage 1 Database Plan*

## Decision

- **PostgreSQL 17** throughout, hosted in Sydney.
- **Months 1-2:** Supabase (Sydney), **test data only**. **Month 3 onward:** Amazon RDS for
  PostgreSQL 17 (Multi-AZ). The same migration files build the RDS database; no data is moved.
- **Four schemas, none public:** `platform`, `content`, `clinical`, `media`. (The runner keeps
  its own bookkeeping in a separate `migrations` schema.)
- ~~**Plain numbered SQL migrations** in `db/migrations`, applied by `python -m brivo.migrate`.
  Forward-only; applied files are never edited (the runner checks a SHA-256 checksum).~~
  *Superseded by [ADR 0004](0004-alembic-migrations.md): Alembic migrations.*
- **Roles:** `brivo_owner` owns the schemas and runs migrations; `brivo_app` is used by the
  API and worker, with `NOBYPASSRLS`. Created once per environment by `db/bootstrap-roles.sql`.
- **Row-Level Security** on every tenant table via `platform.enable_tenant_rls(table)`, keyed on
  `org_id = platform.current_org_id()`, which the API sets per transaction.
- **IDs:** UUIDv7, generated by the application.

## Consequences

Only standard PostgreSQL features are used, so the schema runs unchanged on Supabase and RDS.
Supabase-specific features (Auth, Storage, `auth.uid()`, its built-in roles) must not be used.
